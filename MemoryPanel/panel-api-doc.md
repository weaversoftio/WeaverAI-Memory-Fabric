# MemoryPanel API reference

> Service: MemoryPanel (control panel), port `8125`

---

## 1. Common conventions

### 1.1 Base URL and port

| Item | Value |
|---|---|
| Base URL | `/api/v1` (except `/health`) |
| Port | 8125 |
| Methods | **everything is `POST`** (RPC style) except `GET /health` and `GET /api/v1/meta/instances` |
| Content-Type | `application/json` |

### 1.2 Auth

Almost every business endpoint relies on these headers (checked by the `validatePanelMetaHeaders` middleware):

| Header | Required | Description |
|---|---|---|
| `x-wamf-service-id` | yes | instance ID, used to find the target kernel gateway (`instanceRegistry.resolve`) |
| `x-wamf-user-key` | yes* | the current user's key, used by the kernel's `auth/verify` to resolve the caller's identity |
| `x-request-id` | no | passed through to `request_id` in the response envelope, for log correlation |

> `*` Exceptions: `POST /meta/auth/verify` (no user-key, since it is the key check itself); `POST /knowledge/status-callback` (S2S callback, no browser headers); `GET /health` and `GET /meta/instances` (no auth).

### 1.3 Response envelope

Every business endpoint returns:

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { }
}
```

| Field | Type | Description |
|---|---|---|
| code | number | `0` success; non-zero failure |
| message | string | always `"ok"` on success; on failure an upper-case underscore error enum (a stable contract the frontend branches on) |
| request_id | string | request ID, from `x-request-id` or generated by the server |
| data | any | business data; `null` on failure |

> Exception: `GET /health` and `GET /meta/instances` **return no envelope**, just bare JSON (see §3.1).

### 1.4 HTTP status mapping

`HTTP status = envelope.code`, mapped as:

| envelope.code | HTTP status |
|---|---|
| `0` | `200` |
| `400 ~ 599` | same as `code` |
| anything else | `502` |

### 1.5 Pagination

- Kernel list endpoints default to `DEFAULT_PAGINATION = { limit: 20 }`: **when the frontend calls a `meta/*` list action directly without a limit, only the first 20 items come back**.
- Panel-level aggregating/business endpoints (e.g. `chat-memory/*`, `knowledge/*/team-assets`) already page through everything internally; the frontend doesn't need to page.
- `task/list-with-agents` caps `limit` at 200; without it the kernel returns the default 20 items, but the response's `limit` field echoes 50 (a known inconsistency, see §3.5).

### 1.6 Idempotency

- Knowledge create endpoints (`wiki/create`, `code-graph/create`) are idempotent by name/resource: creating the same thing again returns the existing resource instead of an error.
- Create-type `meta/*` actions (`user/create`, `team/create`, `agent/create`, `task/create`) check for duplicates in the Panel first; a duplicate name returns `409` with a readable message.

### 1.7 Request ID chain

`x-request-id` (optional) → passed into the envelope's `request_id` → also sent when forwarding to the kernel, for cross-service log correlation.

Health check. No auth, no request body; **returns bare JSON (no envelope)**.

**Response**

```json

```

Returns the instance list. No auth, no request body; **returns bare JSON (no envelope)**.

**Response**

```json
{
  "instances": [

```

| Field | Type | Description |
|---|---|---|

| instances[].proxy_endpoint | string? | optional client connection baseUrl; the frontend falls back to `gateway_endpoint` when it's missing |

## 3.2 Transparent metadata proxy

### POST /meta/*

Forwards `{ action, ...payload }` to the kernel's `/v3/meta/{action}` and passes the envelope back unchanged. This is the Panel's single entry point to the kernel's metadata plane (user/team/agent/task/asset/acl, etc.).

**Auth**: `x-wamf-service-id` + `x-wamf-user-key` (only `auth/verify` needs no user-key).

**Forwarding semantics**:
- the whole request body goes to the matching kernel action; the response envelope comes back unchanged.
- the last path segment is the action name (e.g. `POST /meta/agent/list` → kernel `agent/list`).
- actions outside the allow-list return `404 UNKNOWN_META_ACTION`; `agent-fixed-asset/*` returns `501 NOT_IN_SCOPE` (those operations are called directly inside the Panel's business routes, see §3.4/§3.10).

**Open actions (53)**:

| Entity | Actions |
|---|---|
| user | create, create-with-key, get, delete, list |
| user-key | create, list, get, revoke, update |
| team | create, get, update, delete, list |
| team-member | add, remove, list, get |
| agent | create, get, update, delete, list, archive, set-default-template, get-default-template |
| task | create, get, update, delete, list, archive |
| task-agent | link, unlink, list |
| participation-log | append, list |
| asset | create, get, update, delete, list, list-accessible, touch-usage |
| acl | grant, revoke, list, check |
| auth | verify |
| instance-quota | get |
| config/user | get, set |

**Not open (`501 NOT_IN_SCOPE`)**: `agent-fixed-asset/set`, `agent-fixed-asset/list`, `agent-fixed-asset/list-with-detail`, `agent-fixed-asset/summary-by-agents`.

**Special handling in the Panel (not pure pass-through)**:

| Action | Behaviour |
|---|---|
| `user/create`, `user/create-with-key`, `team/create`, `agent/create`, `task/create` | first checks for a duplicate name/username/title; a duplicate returns `409` with a readable message |
| `agent/set-default-template` | **not forwarded to the kernel**; the Panel writes a local template file; needs `system_admin`, otherwise `403 permission_denied`; missing `team_id`/`template` returns `400 INVALID_PARAM` |
| `agent/get-default-template` | **not forwarded to the kernel**; the Panel reads the local template file |
| `team-member/add` | on success, copies the template assets to the default Agent asynchronously (best-effort) |
| `user/list` | hides the internal `knowledge-service` billing user |

**Example** (`agent/create`):

```json
// request
POST /api/v1/meta/agent/create
{ "team_id": "t_1", "owner_user_id": "u_1", "name": "Release assistant" }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "agent_id": "agt_xxx", "name": "Release assistant" }
}
```

## 3.3 Transparent skill data-plane proxy

### POST /skill/*

Forwards `{ action, ...payload }` to the kernel's `/v3/skill/{action}` and passes the envelope back unchanged.

**Auth**: `x-wamf-service-id` + `x-wamf-user-key` (mandatory; skills need the owner identity).

**Differences from `/meta/*`**:
- the skill data plane has its own storage (`skill_id` prefix `skl-`): readable within the team, writable by the owner agent.
- identity fields (`user_id` / `team_id` / `agent_id` / `task_id`) go in the **body**, not headers.
- pagination uses nested `pagination.{limit, offset}`, passed through in the body unchanged.

**Open actions (15)**:

| Action | Description |
|---|---|
| create | creates a skill |
| update | full update |
| patch | partial update |
| delete | delete |
| get | single lookup |
| list | paged list |
| search | search |
| versions | version list |
| files/write | writes files |
| files/remove | deletes files |
| files/read | reads a file |
| listing | directory listing |
| extract | extraction |
| export | export |
| conversation/add | conversation append (the main skill extraction path, added to the allow-list 2026-08) |

**Errors**: an unknown action returns `404 UNKNOWN_SKILL_ACTION`.

**Example** (`list`):

```json
// request
POST /api/v1/skill/list
{
  "user_id": "u_1",
  "team_id": "t_1",
  "filters": { "status": ["active"] },
  "pagination": { "limit": 50, "offset": 0 }
}

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "skill_id": "skl_1", "name": "code-review", "owner_agent_id": "agt_1" } ],
    "total": 1
  }
}
```

## 3.4 Chat-Memory

> The common memory block (MemoryBlock) response shape:

| Field | Type | Description |
|---|---|---|
| id | string | asset ID (`chat_memory-{team}-{agent}` or a user-created `mem-xxx`) |
| title | string | block title |
| summary | string | summary (currently placeholder text) |
| uploaded_by_user_id | string | owner user ID |
| updated_at_ms | number | update time (ms epoch) |
| layer_counts | object | `{ L0_messages, L1, L2, L3 }` (currently a placeholder, all 0) |
| scope | string | `team` / `private` |
| agent_id | string | linked agent (returned by some endpoints) |

### POST /chat-memory/team-assets

The memory assets shared in the team (`visibility=team`, any owner). **Note: the MemoryBlocks from this endpoint have no `scope` field** (everything on the team assets tab is shared by definition).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | yes | team ID |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| items | MemoryBlock[] | the team's shared memory blocks (without `scope`) |
| total | number | total |

**Example**

```json
// request
{ "team_id": "t_1" }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "chat_memory-t_1-agt_1", "title": "Release assistant", "summary": "0 L1 · 0 L2 · 0 L3" } ],
    "total": 1
  }
}
```

### POST /chat-memory/agent-fixed

The fixed asset bindings of type `chat_memory` for a given Agent. **Only visible to the Agent's owner**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| agent_id | string | yes | Agent ID |

**Response** `data`: `{ items: MemoryBlock[], total }`; each item has `scope` (`team`/`private`) so the frontend can grey out items "made private by the owner".

**Errors**: `MISSING_AGENT_ID`, `INVALID_USER_KEY`, `AGENT_NOT_FOUND`, `NOT_YOUR_AGENT`.

### POST /chat-memory/my-agents

The "My asset allocation" tab: returns every Agent I own, with one memory block per Agent (`block.id = chat_memory-{team}-{agent}`).

**Request body**: `{ team_id: string }`

**Response** `data`: `{ items: MemoryBlock[], total }`; each item has `agent_id` and `scope` (from the visibility of that agent's own memory).

**Errors**: `MISSING_TEAM_ID`, `INVALID_USER_KEY`.

### POST /chat-memory/mine

The memory assets I (the owner) own.

**Request body**: `{ team_id: string }`

**Response** `data`: `{ items: MemoryBlock[], total }`.

**Errors**: `MISSING_TEAM_ID`, `INVALID_USER_KEY`.

### POST /chat-memory/create

Creates a standalone memory asset (UserAsset, `mem-xxx`).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | yes | team ID |
| title | string | yes | title, ≤ 200 characters |
| scope | string | no | `team` (default) / `private` |
| description | string | no | description |

**Response** `data`: `MemoryBlock` (`id` is the new `mem-xxx`).

**Errors**: `MISSING_TEAM_ID`, `INVALID_TITLE`, `INVALID_USER_KEY`.

**Example**

```json
// request
{ "team_id": "t_1", "title": "Product requirement notes", "scope": "team" }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "id": "mem_xxx", "title": "Product requirement notes", "scope": "team" }
}
```

### POST /chat-memory/import

Imports past conversations into the L0 of an Agent's memory pool (through the data plane's `/v3/conversation/add`; no new asset is created).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | yes | team ID |
| agent_id | string | yes | target Agent |
| messages | object[] | yes | `[{ role, content, ts? }]`, ≤ 100 items |
| session_id | string | no | session ID; `imported-{ts}` is generated if missing |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| imported | boolean | always `true` |
| block_id | string | `chat_memory-{team}-{agent}` |
| session_id | string | the session actually used |
| accepted_count | number | number written |

**Errors**: `MISSING_TEAM_ID`, `MISSING_AGENT_ID`, `MISSING_MESSAGES`, `TOO_MANY_MESSAGES`, `NO_VALID_MESSAGES`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`.

**Example**

```json
// request
{
  "team_id": "t_1",
  "agent_id": "agt_1",
  "messages": [ { "role": "user", "content": "Can you look at this bug?" } ]
}

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "imported": true, "block_id": "chat_memory-t_1-agt_1", "accepted_count": 1 }
}
```

### POST /chat-memory/patch-scope

Changes memory visibility (team ↔ private).

**Request body**: `{ block_id: string, scope: "team" | "private" }`

**Response** `data`: `{ updated: true, id, scope }`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_SCOPE`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`.

### POST /chat-memory/set-agent-fixed

Sets an Agent's fixed memories in bulk (atomic validation + a single full set).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| agent_id | string | yes | target Agent |
| team_id | string | yes | team ID |
| block_ids | string[] | yes | memory block IDs to bind (including its own `chat_memory-{team}-{agent}`) |

**Response** `data`: `{ updated: true, agent_id, block_ids }`.

**Errors**: `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `IMPORT_LIMIT_EXCEEDED`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `TEAM_MISMATCH`, `ASSET_NOT_SHARED`.

### POST /chat-memory/allocate

Allocates (borrows) a shared memory to a given Agent, with a "borrowed ≤ 2" check.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | yes | memory block ID |
| agent_id | string | yes | target Agent |
| team_id | string | yes | team ID |

**Response** `data`: `{ allocated: true, agent_id, block_id }`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `TEAM_MISMATCH`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `ASSET_NOT_SHARED`, `IMPORT_LIMIT_EXCEEDED`; a repeated allocation returns `409` with a readable message ("This memory is already allocated to this Agent."); allocating an agent's own `chat_memory-{team}-{agent}` back to itself returns `400` with a readable message ("An Agent's own memory cannot be allocated back to itself.").

**Example**

```json
// request
{ "block_id": "chat_memory-t_1-agt_2", "agent_id": "agt_1", "team_id": "t_1" }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "allocated": true, "agent_id": "agt_1", "block_id": "chat_memory-t_1-agt_2" }
}
```

### POST /chat-memory/unbind

Unbinds a borrowed memory from an Agent.

**Request body**: `{ block_id: string, agent_id: string, team_id: string }`

**Response** `data`: `{ unbound: true, agent_id, block_id }`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `CANNOT_UNBIND_SELF_CHAT_MEMORY`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `BINDING_NOT_FOUND`.

### POST /chat-memory/layer

Lazy-loads memory content per layer. Resolves team/agent from `block_id`, then calls the kernel data plane.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | yes | memory block ID |
| layer | string | yes | `L0` / `L1` / `L2` / `L3` |
| limit | number | no | valid range `(0, 200]`; omitted, ≤0 or >200 falls back to 50 (no clamping, unlike the clamping in task/search) |
| offset | number | no | default 0 |
| before_ts | string | no | L0 cursor pagination (ISO8601; for the next page, pass the time of the last item on the previous page) |
| time_start | string | no | start of the time filter (L0/L1 only) |
| time_end | string | no | end of the time filter (L0/L1 only) |
| path | string | no | file path when reading a single L2 item |

**Data source per layer**: L0 → `/v3/conversation/query`; L1 → `/v3/atomic/query`; L2 → `/v3/scenario/ls` (list) / `/v3/scenario/read` (with `path`); L3 → `/v3/core/read`.

**Response** `data`: `{ layer, items, total, limit, offset }`, each item in `items` being:

| Field | Type | Description |
|---|---|---|
| id | string | item ID (always `"core"` for L3) |
| title | string | title (role@session for L0, the type for L1, the path for L2, always `"core memory"` for L3) |
| role | string? | L0 only: message role (`user`/`assistant`/`tool`, etc.) |
| body | string | content |
| tags | string[] | tags |
| refs | string[] | references (currently always empty) |
| created_at | string | time (ISO) |

**Read permission**: owner / `visibility=team` / already borrowed by an agent the caller owns; any one is enough, otherwise `403 ASSET_NOT_ACCESSIBLE`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `ASSET_NOT_ACCESSIBLE`, `RANGE_TOO_LARGE` (the time filter range is too large for the backing store), `LAYER_FETCH_ERROR`.

**Example** (L1)

```json
// request
{ "block_id": "chat_memory-t_1-agt_1", "layer": "L1", "limit": 20, "offset": 0 }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "layer": "L1",
    "items": [ { "id": "rec_1", "title": "atomic", "body": "Release goes out next Monday", "tags": [], "refs": [] } ],
    "total": 1,
    "limit": 20,
    "offset": 0
  }
}
```

### POST /chat-memory/clear

Clears all content of some memories in one step while keeping the assets (ownership/bindings/ACL unchanged). **Asset owner only**.

**Request body**: `{ memory_ids: string[] }` (≤ 100 after deduplication).

**Response**: the result of the kernel's `/v3/chat-memory/clear`, passed through.

**Errors**: `MISSING_MEMORY_IDS`, `TOO_MANY_MEMORY_IDS`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `CLEAR_FAILED`.

### POST /chat-memory/layer-delete

Batch delete from the L0/L1 lists. **Asset owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | yes | memory block ID |
| layer | string | yes | `L0` / `L1` |
| message_ids | string[] | for L0 | message IDs, ≤ 5000 |
| session_ids | string[] | for L0 | session IDs, ≤ 100 |
| ids | string[] | for L1 | record IDs, ≤ 5000 |

**Response**: the result of the kernel's `/v3/conversation/delete` or `/v3/atomic/delete`, passed through (with `deleted_count`).

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `TOO_MANY_IDS`, `MISSING_IDS`, `LAYER_DELETE_FAILED`.

### POST /chat-memory/layer-add

Adds one L1 memory directly, without LLM extraction (e.g. from the memory MCP's `memory_add`). **Asset owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | yes | memory block ID (`chat_memory-{team}-{agent}`) |
| layer | string | no | only `L1` (default) |
| content | string | yes | the memory, one standalone statement |
| type | string | no | `work_fact` (default), `work_task`, `work_method`, `work_artifact`, `persona`, `episodic`, `instruction` |
| priority | number | no | -1–100, default 50 |
| background | string | no | scene name to group it under |

**Data source**: `/v3/atomic/add`.

**Response**: the kernel result passed through: `{ id, version, type, created_at }`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `MISSING_CONTENT`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `LAYER_ADD_FAILED`.

### POST /chat-memory/layer-update

Edits the content of one memory layer. **Asset owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | yes | memory block ID |
| layer | string | yes | `L1` / `L2` / `L3` |
| id | string | required for L1/L2 | L1 record primary key / L2 file path |
| content | string | yes | new content |
| summary | string | no | L2 summary |

**Data source per layer**: L1 → `/v3/atomic/update`; L2 → `/v3/scenario/write` (the META header is stripped automatically); L3 → `/v3/core/write`.

**Response**: the result of the matching kernel write endpoint, passed through.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `MISSING_CONTENT`, `MISSING_ITEM_ID`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `LAYER_UPDATE_FAILED`.

### POST /chat-memory/search

Keyword search per layer (agent-level recall across sessions).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | yes | memory block ID |
| layer | string | no | `L0` / `L1`, default `L1` |
| query | string | yes | search terms |

### 4.2 Error message enums

> `message` is a stable contract the frontend branches on; new error codes must be added to this table.
>
> Three kinds of `message` are exceptions (built by the Panel, not pure enums):
> 1. **Data-plane failures** (`LAYER_FETCH_ERROR` / `CLEAR_FAILED` / `LAYER_DELETE_FAILED` / `LAYER_UPDATE_FAILED` / `SEARCH_FAILED`): the actual value is `"<CODE>: <err.message>"` (with a `: detail` suffix), so the frontend should use `startsWith(CODE)` rather than an exact match.
> 2. **The 400 of `POST /knowledge/status-callback`**: the `message` is a lowercase English sentence (`"wiki_id and progress fields are required"` / `"knowledge_id, type, status are required"`), not an enum. It's an S2S callback the frontend doesn't consume directly, so this can be ignored.
> 3. **Readable sentences** (`respondControlError` puts a sentence in directly, not an enum, so `startsWith(CODE)` doesn't match either): the `meta/*` create duplicate check 409 ("A … named "…" already exists. Please choose another name and try again."), the `chat-memory/allocate` repeated allocation 409 ("This memory is already allocated to this Agent."), and allocating an agent to itself 400 ("An Agent's own memory cannot be allocated back to itself."). The frontend has to fall back on the message text or the HTTP status; it can't branch on a CODE enum here.
