# v3 API reference · Volume 1: MemoryCore

> Service: MemoryCore (the memory kernel), port `8420`
> This volume covers every `/v3/*` endpoint MemoryCore exposes. MemoryKnowledge (`/v3/wiki`, `/v3/code-graph`, etc.) is in volume 2, MemoryProxy in volume 3.
> Maintenance rule: an endpoint change (new endpoint / changed field / changed error code) must update this document in the same PR.

---

## 1. Common conventions

### 1.1 Service and port

| Item | Value |
|---|---|
| Service | MemoryCore (memory kernel gateway) |
| Port | 8420 |
| Methods | all `POST` (v3 is RPC style, no GET) |
| Content-Type | `application/json` |
| Health check | `GET /health` (**not v3**, no auth, returns bare JSON `status/version/uptime/stores/services`; outside this document) |

### 1.2 Response envelope

Every v3 endpoint returns:

```json
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { } }
```

| Field | Type | Description |
|---|---|---|
| code | number | `0` success; non-zero failure. **Note**: the skill module's failure codes are 5-digit numbers (see §1.6) |
| message | string | always `"ok"` on success; an error description on failure (format in §1.6) |
| request_id | string | request ID, from `x-request-id` or generated by the server |
| data | any | business data; usually missing or null on failure |

### 1.3 Pagination

- data-plane list/query endpoints: `limit` default `20`, max `100`; `offset` default `0` (`paginationSchema`).
- meta list endpoints: `limit` default `20`, max `100`, `offset` default `0` (`DEFAULT_PAGINATION`); the response is always `{ items, total, limit, offset }`.
- skill `list`: `limit` max `1000`; skill `search`: `top_k` max `50`.
- knowledge `list`: `pagination.limit` max `1000` (`knowledgeListRequestSchema`, same as skill list).
- memory-prompt / generation-log list: `limit` default `20`, max `100`.

### 1.4 Auth layers

v3 endpoints fall into four auth layers (all need `Authorization: Bearer <KERNEL_AUTH_TOKEN>` as the Layer 1 gateway check; not enforced when `apiKey` isn't configured):

| Layer | Routes | Extra auth |
|---|---|---|
| data plane | `/v3/conversation·atomic·scenario·core/*`, `/v3/skill/*`, `/v3/knowledge/*`, `/v3/chat-memory/*`, `/v3/memory-prompt/*`, `/v3/memory-generation-log/*` | `x-wamf-service-id` (instance ID) |
| metadata plane | `/v3/meta/*` | `x-wamf-service-id` + `x-wamf-user-key` (user key; `auth/verify` needs no user-key) |
| internal operations | `/v3/internal/meta/*` | Bearer only, user-key **not parsed** |
| instance destroy | `/v3/instance/destroy` | Bearer apiKey only (v1 style, an ops endpoint) |

> Isolation fields: the data-plane `team_id / agent_id / user_id / task_id` can come from the **body or headers** (`x-wamf-team-id` / `x-wamf-agent-id` / `x-wamf-user-id` / `x-wamf-task-id`); the body wins. The v3 data plane **enforces** team + agent + user isolation (missing values fall back to the `default` bucket).

### 1.5 Error code meanings (data plane, general)

| code | Meaning |
|---|---|
| 400 | invalid parameters (missing ID, mutually exclusive fields, empty input) |
| 401 | auth failed |
| 403 | ownership consistency check failed (e.g. `(team_id, agent_id)` isn't a valid ownership, `task_id` doesn't belong to `team_id`) |
| 404 | resource doesn't exist or doesn't belong to the current call context (existence isn't revealed) |
| 409 | concurrency race timed out |
| 422 | schema passed but a business rule failed |
| 429 | rate limit / quota exceeded |
| 500 | internal error |
| 503 | dependency unavailable (LLM / storage) |

### 1.6 Error message formats (three kinds; important)

Different modules use different failure `message` formats, and the frontend has to handle each:

| Module | message format | HTTP code | Example |
|---|---|---|---|
| meta / internal-meta | `"{error_code}: {detail}"` (error_code in snake_case) | standard 4xx/5xx | `"team_not_found: not found: t_1"` |
| skill | the raw `SkillCoreError.message` | **5-digit number** (40001, etc.) | `"SKILL_NOT_FOUND: ..."` |
| data plane / knowledge / chat-memory / memory-prompt / generation-log | plain text or an upper-case enum | standard 4xx/5xx | `"Knowledge not found"`, `"MEMORY_PROMPT_NOT_FOUND"`, `"Store not available"` |

## 3. Endpoint details

## 3.1 L0–L3 data plane (19)

> Memory layers: L0 raw conversation (conversation), L1 memory atoms (atomic, of three kinds: episodic/persona/instruction), L2 scene files (scenario), L3 core persona (core).
> Every endpoint takes the 4 ID isolation fields (`team_id/agent_id/user_id/task_id`, body or header).
> Delete endpoints such as `conversation/delete` and `atomic/delete` trust Bearer + `x-wamf-service-id` and do no user-level auth (consistent with the check the panel does before forwarding).

### POST /v3/conversation/add

Writes L0 raw conversation messages. After a successful write the L1 extraction pipeline is triggered asynchronously (`notifyPipeline`).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| session_id | string | yes | business session ID |
| messages | object[] | yes | 1–100 items, `{ role: "user"\|"assistant", content: 1–8192 characters, timestamp?, recorded_at? }` |
| team_id / agent_id / user_id / task_id | string | no* | isolation fields (*v3 enforces team+agent+user; missing values fall back to the default bucket) |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| accepted_ids | string[] | IDs of the accepted messages |
| accepted_versions | string[] | in the same order as accepted_ids; always `v1` for new messages |
| total_count | number | number accepted |

**Example**

```json
// request
{ "session_id": "sess_1", "messages": [ { "role": "user", "content": "Can you look at this bug?" } ] }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "accepted_ids": ["msg_1"], "accepted_versions": ["v1"], "total_count": 1 }
}
```

### POST /v3/conversation/query

Paged L0 message query.

**Request body**: `session_id?`, `limit?` (default 20 / max 100), `offset?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ messages: ConversationItem[], total }`, with ConversationItem = `{ id, version, role, content, timestamp?, recorded_at?, session_id?, team_id?, user_id?, agent_id? }`.

### POST /v3/conversation/search

Keyword search over L0 messages.

**Request body**: `query` (1–2048), `limit?` (default 5 / max 100), `session_id?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ messages: (ConversationItem & { score })[] }`.

### POST /v3/conversation/delete

Batch-deletes L0 by message_ids or session_ids.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| message_ids | string[] | one of the two | ≤5000 items |
| session_ids | string[] | one of the two | ≤100 items |
| session_id | string | no | @deprecated, use session_ids |

**Response** `data`: `{ deleted_count: number }`.

**Errors**: `400` (at least one of the two is required).

### POST /v3/conversation/count

L0 count (**v3 only, no v2 entry point**).

**Request body**: `session_id?`, `time_start?`, `time_end?`.

**Response** `data`: `{ total: number }`.

---

### POST /v3/atomic/add

Writes one L1 memory directly, without LLM extraction (**v3 only**). Used by agents that decide a fact is worth remembering, e.g. through the memory MCP. The record belongs to the request's team + agent + user like an extracted memory, and the next L2 scene run picks it up.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| content | string | yes | 1–8192 characters, one standalone statement |
| type | string | no | `work_fact` (default), `work_task`, `work_method`, `work_artifact`, `persona`, `episodic`, `instruction` |
| priority | integer | no | -1–100, default 50 (same scale as extraction; -1 = strict global instruction) |
| background | string | no | scene name to group it under (≤512) |
| team_id / agent_id / user_id / task_id | string | team, agent, user: yes | isolation fields |

**Response** `data`: `{ id, version: "v1", type, created_at }`.

**Errors**: `400` (schema, or a missing team/agent/user), `503` (store unavailable). Not written to the audit table, which records only update/delete.

### POST /v3/atomic/update

Updates one L1 memory atom (the version is incremented).

**Request body**: `id`, `content` (≤8192), `background?` + isolation fields.

**Response** `data`: `{ id, version, updated_at }`, where `version` is a **string** `"v{n}"` (e.g. `"v2"`).

> ⚠️ Inconsistent version type: `update` returns the string `"v{n}"`, but `query`/`search` return a **number** (`r.version ?? 0`). The root cause is in the code (`generated/types.ts` declares `string "v1"`, but `v2-schemas.ts` overrides it as `number`); the docs can't satisfy both, so the frontend has to handle each endpoint separately.

### POST /v3/atomic/query

Paged L1 query.

**Request body**: `type?` (episodic/persona/instruction), `time_start?`, `time_end?`, `limit?`, `offset?` + isolation fields.

**Response** `data`: `{ items: AtomicDetail[], total }`.

**AtomicDetail** fields:

| Field | Type | Description |
|---|---|---|
| id | string | atom ID |
| version | number | current version (**query/search return a number**; note that `update` returns the string `"v{n}"`, an inconsistent type) |
| type | string | `episodic` / `persona` / `instruction` |
| background | string? | background |
| content | string | body |
| created_at / updated_at | string | ISO times |
| team_id / agent_id / user_id / task_id | string? | isolation fields |

**Example**

```json
// request
{ "type": "episodic", "limit": 20, "offset": 0 }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "rec_1", "version": 1, "type": "episodic", "content": "Release goes out next Monday", "created_at": "2026-08-20T00:00:00Z", "updated_at": "2026-08-20T00:00:00Z" } ],
    "total": 1
  }
}
```

### POST /v3/atomic/search

Keyword search over L1.

**Request body**: `query` (1–2048), `limit?` (default 5 / max 100), `type?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ items: (AtomicDetail & { score })[] }`.

### POST /v3/atomic/delete

Batch-deletes L1 by id.

**Request body**: `ids: string[]` (≤5000).

**Response** `data`: `{ deleted_count: number }`.

### POST /v3/atomic/count

L1 count (**v3 only**).

**Request body**: `type?`, `time_start?`, `time_end?`.

**Response** `data`: `{ total: number }`.

---

### POST /v3/scenario/ls

L2 scene file list (everything at once, no pagination).

**Request body**: `path_prefix?` (empty/omitted = list recursively from the root) + isolation fields.

**Response** `data`: `{ entries: ScenarioEntry[], total }`.

**ScenarioEntry**: `{ path, summary?, version, team_id?, agent_id?, created_at, updated_at }` (directories have `version=0` and a path ending in `/`).

### POST /v3/scenario/read

Reads one L2 file.

**Request body**: `path` (relative, checked against traversal), `version?` + isolation fields.

**Response** `data`: `{ path, version?, content, created_at, updated_at }`. **A missing file returns 200 with content/created_at/updated_at null (not 404)**.

### POST /v3/scenario/write

Writes an L2 file (the META header is stripped automatically).

**Request body**: `path`, `content`, `summary?` + isolation fields.

**Response** `data`: `{ path, version, updated_at }`.

### POST /v3/scenario/rm

Deletes an L2 file/directory.

**Request body**: `path` (ending in `/` = delete a directory, otherwise a single file) + isolation fields.

**Response** `data`: none (`successEnvelope(undefined)`).

### POST /v3/scenario/count

L2 count (**v3 only**).

**Request body**: `path_prefix?`.

**Response** `data`: `{ total: number }`.

---

### POST /v3/core/read

Reads the L3 core memory (persona.md).

**Request body**: `version?` + isolation fields (the body may be empty).

**Response** `data`: `{ content, version?, team_id?, agent_id?, created_at, updated_at }`. **A missing file returns 200 with content null**.

### POST /v3/core/write

Writes the L3 core memory (Scene Navigation and leading/trailing whitespace are stripped automatically).

**Request body**: `content` + isolation fields.

**Response** `data`: `{ version, updated_at }`.

### POST /v3/core/count

L3 count (**v3 only**).

**Request body**: `{}` (an empty object).

**Response** `data`: `{ total: number }`.

## 3.2 Skill (17)

> The skill data plane has its own storage (`skill_id` prefix `skl-`); readable within the team, writable by the owner. Identity fields go in the body.
> Failure codes are **5-digit numbers** (see §1.6); the error code mapping is in appendix §4.2.

### POST /v3/skill/create

Creates a skill (on success it's registered as a meta_asset and bound to the owner agent automatically).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| name | string | yes | ≤64 characters, must equal frontmatter.name |
| content | string | yes | full SKILL.md text |
| resources | object[] | no | ≤100 items, `{ path ≤512, content, encoding: "utf-8"\|"base64", mime_type?, is_executable? }` |
| metadata | object | no | custom metadata |
| team_id / agent_id / user_id / task_id | string | see below | write endpoints require team+agent+user |

> Constraint: `agent_id` must be namespaced by `team_id` (an agent requires a team).

**Response** `data`: `SkillSummary` (described at the end of §3.2).

**Errors**: `40001` (parameters/frontmatter mismatch), `42201` (duplicate name), `4291` (quota exceeded), `50304` (repeated skill_id collisions).

**Example**

```json
// request
{ "team_id": "t_1", "agent_id": "agt_1", "user_id": "u_1", "name": "code-review", "content": "---\nname: code-review\n---\n# Code Review" }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "skill_id": "skl_1", "name": "code-review", "version": 1, "status": "active", "owner_user_id": "u_1", "owner_agent_id": "agt_1", "team_id": "t_1" }
}
```

### POST /v3/skill/update

Full update (optimistic locking).

**Request body**: `skill_id`, `expected_version` (≥1), `content` + id fields.

**Response** `data`: `SkillSummary`.

**Errors**: `40901` (stale version; data carries `current_version`), `40401`, `40301`.

### POST /v3/skill/patch

Partial replacement (optimistic locking, string patch).

**Request body**: `skill_id`, `expected_version`, `old_string`, `new_string`, `replace_all?` + id fields.

**Response** `data`: `SkillSummary`.

**Errors**: `40901`, `42202` (patch not unique), `40401`.

### POST /v3/skill/delete

Hard delete (**changed 2026-07; it used to be a soft delete**): deletes every version + clears storage, cascading to meta_asset / ACL / agent bindings.

**Request body**: `skill_id`, `expected_version`, `team_id?` + id fields.

**Response** `data`: `{ skill_id, archived: boolean }`, where `archived` means "deleted successfully", `deleted > 0` (**not an archived state**; the real delete reuses the field).

**Errors**: `40401`, `40901`, `40301`, `40302`.

### POST /v3/skill/get

Gets details by skill_id (content / manifest optional).

**Request body**: `skill_id`, `version?`, `include_content?` (default true), `include_manifest?` (default true) + id fields.

**Response** `data`: `SkillSummary + { content?, manifest?, content_hash?, storage_dir? }`.

**Errors**: `40401`.

### POST /v3/skill/get-by-name

Gets details by the unique `(team_id, agent_id, skill_name)` (so an agent tool call gets the full text in one go).

**Request body**: `team_id` (required), `agent_id` (required), `skill_name` (≤64), `version?`, `include_content?`, `include_manifest?`.

**Response** `data`: same as `get`.

**Errors**: `40401` (returned whenever the name isn't found, without revealing whether the name or the id was missing).

### POST /v3/skill/list

Paged list (only active by default; pass `filters.status` explicitly for archived).

**Request body**: `filters?` (`{ owner_agent_id?, name_prefix?, status?: ["active"\|"archived"] }`), `pagination?` (`{ limit ≤1000, offset }`) + id fields.

**Response** `data`: `{ items: SkillSummary[], total }`.

### POST /v3/skill/search

Searches skills.

**Request body**: `query` (≤2048), `top_k?` (≤50), `mode?` (bm25/embedding/hybrid), `scope?` (="team" searches the team without the owner filter) + id fields.

**Response** `data`: `{ items: (SkillSummary & { score, snippet })[] }`.

### POST /v3/skill/versions

Version list.

**Request body**: `skill_id`, `pagination?` + id fields.

**Response** `data`: `{ items: (SkillSummary & { is_expired })[], total }`.

**Errors**: `40401` (skill doesn't exist).

### POST /v3/skill/files/write

Writes script/resource files.

**Request body**: `skill_id`, `expected_version`, `files` (1–100, same structure as create's resources) + id fields.

**Response** `data`: `SkillSummary`.

### POST /v3/skill/files/remove

Deletes files.

**Request body**: `skill_id`, `expected_version`, `paths` (1–100) + id fields.

**Response** `data`: `SkillSummary`.

### POST /v3/skill/files/read

Reads one file.

**Request body**: `skill_id`, `path`, `version?`, `encoding?` + id fields.

**Response** `data`: `{ content, version, size_bytes, encoding, ... }`.

### POST /v3/skill/export

Exports a skill (zip).

**Request body**: `skill_id`, `version?`, `format?` ("zip" only) + id fields.

**Response** `data`: `{ version, file_count, total_bytes, ... }`.

**Errors**: `41301` (too large).

### POST /v3/skill/listing

Generates the `<available_skills>` injection block (for the agent prompt).

**Request body**: `query?` (≤2048), `char_budget?` (0–64000, default 8000) + id fields.

**Response** `data`: `{ mode: "full"\|"search", listing: string, hits: [{ skill_id, version, name }] }`.

### POST /v3/skill/extract

Direct trigger: manually archives one conversation slice (equivalent to one standalone skill extraction).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| user_id / team_id / agent_id | string | yes | none may contain `\|` |
| messages | object[] | yes | 1–500 items, `{ role: user\|assistant\|tool_call\|tool_result\|system, content, timestamp?, tool_name?, tool_call_id? }` |
| session_id | string | no | generated with an `sx-` prefix if missing |
| space_id | string | no | falls back to auth.serviceId |
| task_id / reason / options | — | no | `options.max_iterations` (1–64) |

**Response** `data`: `{ ok: true, task_id, archived_at_ms, archive_key }`.

### POST /v3/skill/conversation/add

Called synchronously at the end of every conversation turn; it appends + checks thresholds + archives (the main skill extraction path).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| session_id / user_id / team_id / agent_id | string | yes | none may contain `\|` |
| messages | object[] | yes | 1–500 items (roles as for extract; `tool_call`/`tool_result` must carry tool_name+tool_call_id) |
| space_id / task_id | string | no | — |

**Response** `data`: `{ status: "ok"\|"archived", archived?: { task_id, archived_at_ms, archive_key, reason } }`, with `archived.reason ∈ tool_calls\|bytes\|compressed\|oversize`.

**Errors**: `40001` (schema/validation), `404` (module not enabled), `50001`.

### POST /v3/skill/conversation/force-archive

Manually force-archives the current session buffer (skipping the thresholds).

**Request body**: `space_id`, `user_id`, `team_id`, `agent_id`, `session_id` (all required), `reason?` (≤2000), `task_id?`.

**Response** `data`: `{ status: "empty" \| "archived", task_id?, archived_at_ms?, archive_key?, message? }`.

---

**SkillSummary, the common response shape** (returned by list/create/update, etc.):

| Field | Type | Description |
|---|---|---|
| skill_id | string | globally unique, `skl-` prefix |
| name | string | name |
| description | string? | description |
| version | number | version (monotonically increasing) |
| is_head | boolean | whether this is the head version |
| status | string | `active` / `archived` |
| owner_user_id | string | owner user |
| owner_agent_id | string | owner agent |
| team_id / task_id | string? | ownership |
| created_at_ms / updated_at_ms | number | ms epoch |
| metadata | object? | custom metadata (if any) |

## 3.3 Knowledge details (5)

> Kernel-side CRUD of knowledge **detail metadata** (team-level management plane). The actual storage and operation of wiki/code-graph is in MemoryKnowledge (volume 2); only the detail metadata is recorded here. No binding endpoint (TODO).

### POST /v3/knowledge/create

Upserts a knowledge detail (idempotent).

**Request body**: `knowledge_id`, `type` ("wiki"\|"code-graph"), `service_url` (url), `name`, `summary?` (≤256), `team_id`, `user_id?`, `repo_url?`, `branch?`.

**Response** `data`: `KnowledgeEntity`.

### POST /v3/knowledge/get

Single detail lookup.

**Request body**: `knowledge_id`, `team_id?` (ownership is checked when given).

**Response** `data`: `KnowledgeEntity`.

**Errors**: `404` (doesn't exist), `403` (team mismatch).

### POST /v3/knowledge/update

Partial update.

**Request body**: `knowledge_id`, `team_id?`, `name?`, `summary?`, `service_url?`, `repo_url?`, `branch?`.

**Response** `data`: `KnowledgeEntity`.

**Errors**: `404`, `403`.

### POST /v3/knowledge/delete

Batch delete.

**Request body**: `knowledge_ids` (1–100), `team_id?`.

**Response** `data`: `BatchDeleteResult` (`{ deleted_ids, failed: [{ id, reason }] }`).

### POST /v3/knowledge/list

Paged list by team.

**Request body**: `team_id`, `type?`, `knowledge_ids?` (≤200), `pagination?` (`{ limit ≤1000, offset }`).

**Response** `data`: `KnowledgeListResult`.

**Common errors**: `503` (store unavailable), `400` (schema failure).

**Example** (create)

```json
// request
{ "knowledge_id": "wiki_1", "type": "wiki", "service_url": "https://ks.example.com/wiki_1", "name": "Team wiki", "team_id": "t_1" }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",

}
```

## 3.4 Chat-Memory (1)

### POST /v3/chat-memory/clear

Clears the **content** of some memories (L0/L1/L2/L3) while **keeping the assets** (ownership/bindings/ACL unchanged).

> Auth: Bearer + `x-wamf-service-id` are treated as trusted admin-level credentials; **no user-level owner check** (the panel does the owner check before forwarding).

**Request body**: `memory_ids: string[]` (1–100, deduplicated and empty values removed automatically).

**Response** `data`

| Field | Type | Description |
|---|---|---|
| items | object[] | clear result per memory |
| all_cleared | boolean | true when all succeeded |

**items[] fields**: `memory_id`, `cleared`, `l0_deleted`, `l1_deleted`, `profile_deleted`, `reason?`, `retryable?`, `attempts?`.

**Errors**: `400` (schema), `503` (store/storage/metadata unavailable); a single failed memory doesn't fail the whole call; it shows `cleared=false` in `items[]`.

**Example**

```json
// request
{ "memory_ids": ["chat_memory-t_1-agt_1"] }

// response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "memory_id": "chat_memory-t_1-agt_1", "cleared": true, "l0_deleted": 10, "l1_deleted": 3, "profile_deleted": 1 } ],
    "all_cleared": true
  }
}
```

## 3.5 Memory-Prompt (7)

> Memory prompt management (the L1/L2/L3 prompts); `layer` is lower-case `l1`/`l2`/`l3`.

### POST /v3/memory-prompt/create

Creates a prompt.

**Request body**: `name` (≤100 characters), `layer` ("l1"\|"l2"\|"l3"), `prompt` (≤10000 characters).

**Response** `data`: `{ memory_prompt_id: "mp-xxx", version: 1, created_at_ms }`.

**Errors**: `409` (PROMPT_LIMIT_EXCEEDED, max 500 per instance).

### POST /v3/memory-prompt/get

Three mutually exclusive modes:
1. `memory_prompt_id` → returns one prompt (404 if not active).
2. `layer` + (`team_id`/`agent_id`) → resolves the effective prompt (the built-in fallback if none).
3. `layer` only → returns a list `{ items }`.

**Request body**: `memory_prompt_id?`, `team_id?`, `agent_id?`, `layer?`, `limit?` (default 20), `offset?`, `time_order?` (default desc).

**Errors**: `404` (MEMORY_PROMPT_NOT_FOUND).

### POST /v3/memory-prompt/update

Updates name/prompt.

**Request body**: `memory_prompt_id`, `name?`, `prompt?` (at least one).

**Response** `data`: `{ memory_prompt_id, version, updated_at_ms }`.

**Errors**: `404`.

### POST /v3/memory-prompt/delete

Batch delete (every id must exist).

**Request body**: `memory_prompt_ids` (1–100, deduplicated).

**Response** `data`: deletion result.

**Errors**: `404` (an id doesn't exist).

### POST /v3/memory-prompt/set

Sets the effective prompt (apply / clear).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| action | string | yes | `apply` / `clear` |
| layer | string | yes | l1/l2/l3 |
| memory_prompt_id | string | required for apply | prompt ID |
| team_id | string | no | target team (used with agent_ids) |
| agent_ids | string[] | no | 1–100, needs team_id |

**Response** `data`: `{ affected: number }`.

**Errors**: `404` (prompt doesn't exist), `400` (PROMPT_LAYER_MISMATCH, the prompt's layer doesn't match).

### POST /v3/memory-prompt/setting/list

List of effective settings.

**Request body**: `memory_prompt_id?`, `target_type?` (instance/team/agent), `team_id?`, `agent_id?`, `layer?`, `limit?`, `offset?`, `time_order?`.

**Response** `data`: `{ items }`.

### POST /v3/memory-prompt/log

Operation log (last 7 days by default).

**Request body**: `memory_prompt_id?`, `start_time?`, `end_time?`, `team_id?`, `agent_id?`, `action?` (apply/replace/clear), `limit?`, `offset?`, `time_order?`.

**Response** `data`: `{ items }`.

> Constraint: `start_time`/`end_time` must be given together, and the range must be ≤90 days.

### 3.7.12 Auth (1)

### POST /v3/meta/auth/verify

Checks a user_key and returns the caller's identity. **Needs no user-key** (it is the key check itself; it's in the `V3_NO_USER_KEY_ROUTES` allow-list and handled in the handler, not the auth middleware).

**Request body**: `{ user_key: string }` (`authVerifySchema`; a missing user_key fails Zod validation → `400`).

**Response** `data`: `{ valid: boolean, user: UserPublic | null }` (**nested, not flat**).

- valid key: `{ valid: true, user: { user_id, user_type, username, created_at } }`
- invalid key: `{ valid: false, user: null }` (**HTTP still 200, code=0; no 401**)

> ⚠️ The frontend must check `data.valid` and **must not treat an invalid key as a 401 branch**. `401 unauthorized: invalid_user_key` is what **other meta endpoints** return through the auth middleware (checking the `x-wamf-user-key` header), not what `auth/verify` itself does.

**Example**

```json
// request
{ "user_key": "tk_xxx" }

// response (valid)
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { "valid": true, "user": { "user_id": "usr_1", "user_type": "normal", "username": "alice", "created_at": "2026-08-20T00:00:00Z" } } }

// response (invalid key; note code is still 0)
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { "valid": false, "user": null } }
```
